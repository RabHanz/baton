### What this says about Tessaya's hands

1. **The two highest-value ideas in the sources are cheap to take and Tessaya had neither**: read the tree in one cached call (UFO) and
   batch predictable steps with a live-state stop (UFO, Browser Use, Anthropic and OpenAI all converge on this).
2. **Tessaya was missing the action rung the best driver has**: cua acts through the control's own pattern (accessibility route) before any
   pixel; UFO's `set_edit_text` and cua's `invoke_menu` do the same. Tessaya always moved a mouse to the centre of a rectangle.
3. **Tessaya has no occlusion check.** cua binds a pixel click to the capture it came from; Browser Use drops painted-over nodes. Tessaya
   clicked the centre of an element's rectangle without asking what is on top.
4. **Result classes**: cua's `confirmed / suspected_noop` per action is the best recovery design read. Tessaya reports "Clicked" or "Pressed"
   with no evidence (the Ctrl+C no-op found in #52 is the same problem).
5. **Not worth taking**: a second grounding model per click (Agent S3, UI-TARS) costs a call and, in Tessaya's case, a paid or local model;
   reflection after every step (a second model call per step); OmniParser (needs weights and a GPU, licence per detector version).

## What could not be verified

- Playwright's snapshot and ref assignment (lives in the Playwright core repo, not cloned); incremental snapshot diffs are not in
  `playwright-mcp` at this commit.
- Claude in Chrome internals (closed; third-party reverse notes only). OpenAI and Gemini internals (closed).
- Any latency per step for UFO, Agent S3, UI-TARS, OmniParser or cua: no source ran here (they need a model and, for some, a GPU), and none
  publishes per-step time. Vendor benchmark scores are claims.
- Model-planned runs: a CI runner has no model login and the rules forbid an extra paid service, so **every measurement below uses a scripted
  planner**. It measures the tool path and the number of model turns a planner would spend, not whether a model chooses well.

## Bake-off on the CI Windows desktop

Workflow `Baton hands bake-off` (`.github/workflows/baton-hands-bakeoff.yml`), `windows-2022`, 1024x768, the 13 tasks of
`run.ts` (the 12 of `hands-loop-tasks.md` plus `big-tree`: a folder of 400 files), **three runs of each variant, each on its own runner**.
The code under test is the product's tool table, input driver and UI Automation sidecar. Counting rules, so the numbers can be read honestly:

- **Planner is scripted** (no model login on a runner; no paid service allowed). "Model turns" is what a planner would spend: one per tool call, an
  `act_batch` counting once. It is a proxy, not a measured model call.
- **Success** is judged outside the UI (file bytes, registry value, folder on disk, clipboard, pixel diff), as in `hands-loop-tasks.md`.
- **Call ms** is the harness's wall time per tool call, including one sidecar process start per call (about 60 ms); in the product the sidecar is
  already running, so the absolute numbers are higher than a product call, the differences are the UI Automation work.
- **Misclicks**: in run A the sidecar reported when the topmost thing at a found control's centre is not that control (a click would land
  elsewhere). It reported 0 in every run of every variant (the check was removed afterwards, unproven): **none of the 13 tasks contains an occluded control, so this measures nothing yet.**
- Not measured: whether a model plans well; the gate (harness presses Enter directly); other languages and DPI.

### Variants

| Variant | What it is                                                                                                                                           |
| ------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| base    | the hands as on main: `FindAll`, then five cross-process property reads per element; coordinate clicks; one step per turn                            |
| cache   | UFO's idea: `FindAllBuildCache` with a cache request, properties read from the cache (`uia.rs`)                                                      |
| invoke  | cache, plus acting through the control's own UI Automation pattern with no pointer (cua's accessibility route, UFO's `set_edit_text`)                |
| batch   | cache, plus `act_batch`: up to 6 steps per turn, stops at a failure or when the keyboard's window changes (UFO speculative, Browser Use `multi_act`) |

### Verdicts, by the rule "success rises without more misclicks, or latency falls at equal success"

- **cache: counts.** Success equal (39/39), p50 call 147 to 99 (A) and 137 to 113 (B), p90 364 to 265 and 336 to 257, and 28% off the big-window
  tree read. Shipped (`native/baton-dictation/src/uia.rs`).
- **batch: counts, on turns not on call time.** Success equal, misclicks equal (0), model turns 5.0 to 3.6 (28% fewer), calculator 13 to 4. A batch
  call takes 250-2200 ms by itself, so p50 per call does not fall (130 vs 113); what falls is the number of model round trips, which in a real run is
  where seconds go (not measured here). Shipped as `act_batch`. Each step is judged by the existing `judgeToolCall` as if it were alone (strictest
  verdict wins), a batch stops when `windowKey` changes (a `wait_for` step re-anchors on purpose), and the failure guard still wraps the batch.
- **invoke: does not count, not shipped.** Equal success, p50 99 to 95 ms (inside the run-to-run spread). Its first attempt also **failed 18 of 36
  tasks**: Invoke on a File Explorer list item opens the folder (a double-click), so "select to rename" navigated into it, and the open window then
  failed every later task. Fixed by selecting list, tree and tab items instead (run A is the fixed version), but no gain was shown, so the code is out
  of the product. It might still pay where a mouse click is unreliable (occlusion, user moving the pointer); no task here exercises that.
- **Tree diff, hybrid detection, per-app memory: not built.** Hybrid UIA plus vision needs a detector (OmniParser weights, a GPU, a per-version
  licence check) and a model to read it. Per-app memory needs a model-planned second run. Neither can be measured with a scripted planner. A tree diff
  would save tokens and the scripted planner cannot show that either (tree bytes per task are 1.7 KB).

### Second round: covered controls and effect results (runs 41553192253 and 41623148452)

A 14th task, `covered-control`, puts a topmost banner (a borderless window that does not take the keyboard) over Notepad's menu bar, then
asks for Word Wrap. The planner reacts only to what the tools tell it. A misclick is a `click_element` that went ahead while the sidecar's hit test
said something else was on top at the control's centre. Variants: base; **guard** (refuse the click and name what covers the control: `covered_by`
from UI Automation `ElementFromPoint` plus a parent walk, `uia.rs`); **effects** (before and after readback of the window and control names,
reported as `confirmed` / `suspected_noop` / `unverifiable`, cua's idea); both. Three runs each, 14 tasks, success 42/42 everywhere.

| Variant | Misclicks (3 runs) | Model turns/task | p50 call ms | p90 call ms | Covered-control turns |
| ------- | ------------------ | ---------------- | ----------- | ----------- | --------------------- |
| base    | 3                  | 5.2              | 92          | 267         | 8                     |
| guard   | 0                  | 5.1              | 94          | 265         | 7                     |
| effects | 3                  | 5.1              | 268         | 719         | 7                     |
| both    | 0                  | 5.1              | 277         | 719         | not read              |

- **guard counts and ships.** Misclicks 3 to 0 at equal success and equal latency (p50 92 vs 94 ms), one turn fewer on the covered task. No false
  positive: it refused nothing in the other 13 tasks (48 element clicks, all went ahead). `ScreenCompanion.clickElement` refuses with
  "covered by X, take a screenshot".
- **effects did not count, and the code is not shipped.** It found the no-op one step earlier than base (turns 8 to 7), but guard prevents the
  misclick altogether, and the readback tripled the per-call time (p50 92 to 268 ms: two extra tree reads and a settle wait per click or key; in the
  harness each read also starts a process, about 70 ms, so a product read would cost less, not measured). It also called the banner-dismiss click a
  suspected no-op, because the banner is outside Notepad's tree: a false alarm. cua can afford this because its driver owns the window state; here it
  needs a cheaper readback (the focused control's value, not the whole tree) before it is worth another round.
- **High DPI: not measured.** A hosted runner cannot change display scaling without a sign-out, and the harness cannot change it mid-job. The
  scale-aware code path (`toPhysical` in `inputDriver.ts`) has unit tests but no real-desktop run. Needs a runner image or VM with 150% scaling.

## What is still lacking

1. **No model-planned measurement.** The biggest unknown is how the subscription model does with `act_batch` and the guard on real apps.
   A runner with a model login, or a machine that has one, is the next step; the harness takes a planner swap.
2. **No high-DPI, multi-monitor or non-English task** (see above). Occlusion now has one task; more cases (a dropdown over a control, a toast) would
   test the hit test for false positives.
3. **Effect results** need a cheaper readback before they pay (see above). The no-op class is still the right idea: Tessaya says "Clicked" and
   "Pressed" with no evidence, and the Ctrl+C no-op in #52 is the same problem.
4. **No pixel route when the tree is empty** other than the model's own pointing. The Anthropic `zoom` action and Gemini/OpenAI coordinate models
   show where the closed systems put effort; OmniParser is the open option and costs a GPU.
5. **p50 step time in a real run** (model plus tools) is still not measured; the tables are tool time only.
