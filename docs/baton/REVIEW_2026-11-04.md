### CU-2: approval prompts take the keyboard, and the assistant types without checking where the keys now go

**What is wrong.**

- The gate reads the window with the keyboard **before** it asks him (`agentGate.ts:125`, `focusedWindow()`). Then it opens a prompt that takes focus (`companionWindows.ts:246-248`). When he presses Go ahead, the prompt is destroyed (`:222-228`). Windows hands focus to whatever is next in z-order, which is not necessarily the target.
- Then `type`/`press` run straight to `driverFor().type/press` (`ScreenCompanion.ts:2095-2102`), with **no re-check of the foreground window**. They also never check that it is the window the gate judged, or that it is not a shell.
- The shell check (`focusedShell`) was made against the window as it was before the prompt. That is a time-of-check/time-of-use gap.
- The drive runner does re-check before each key (`screenCompanion.ts:742-760`). The assistant's hands, now the main path (`oneAssistant: true`, `ScreenCompanion.ts:179`), do not.
- The same happens with the capture approval box before the first `ui_tree`: `ui_tree` then reads `GetForegroundWindow()` (`uia.rs:298`) after a 300 ms wait (`ScreenCompanion.ts:935`). If focus has not returned, it lists the wrong window, or Tessaya's own.

**Why it matters.** Typed text in the wrong window is the worst failure computer use can have. The gate is meant to stop text reaching a command line, and this gap lets it through. The vision for hands is "the mouse stays his" (D115) and "checks its own work".

**Fix (small, under 80 lines).**

- In `toolHost.type/press` (and the batch steps), record the window from `focusSoon()` when the gate approves. Re-read it right before sending keys. Refuse with "the window with the keyboard changed" when it differs, or when it is a shell and the gate did not ask about one. `runDrivePlan` already does exactly this.
- Better still, together with CU-1 point 3, never take focus during a hands task, so the gap cannot open.

**Proof on the device.** Turn "Act without asking" off. Ask "write a two-line poem in Notepad". The turn is tainted by `ui_tree`, so `type_text` asks. Answer Go ahead **with the mouse**. Today the turn log's `agent_turn` shows `type_text` "Typed." while the foreground at that moment (log `foreground` before typing) can be Tessaya or another app. After the fix: either Notepad holds the text, or the call is refused with the reason.

**Status.** Fix.

### CU-3: Esc is taken from every app for the whole assistant turn, and the assistant's own Esc kills its turn

**What is wrong.**

- Every assistant turn registers a global Escape (`ScreenCompanion.ts:2216`, `input.holdEscape(dismiss, "drive")`). This is Electron `globalShortcut`, i.e. `RegisterHotKey` (`escapeKey.ts:32`).
- `RegisterHotKey` also fires on **injected** keys. So when the assistant presses `["escape"]` to close a menu or dialog (an allowed key: `inputDriver.ts:32`), the app never receives it. Instead `dismiss()` runs `dropOperator()`, which disposes the agent session (`:703-713`, `:1019-1025`), and the turn ends half-done.
- Drive does the same (`:1516`): a plan step that presses Esc cancels the drive.
- His own Esc in any app is also swallowed for the whole turn, which can run up to 30 minutes (`OPERATOR_TURN_MS`). That contradicts SCREEN.md ("Esc is left to your apps").

**Why it matters.** Esc is the standard way to recover in a GUI (close the wrong menu, dismiss a popup). The prompt tells the model to "change the plan: … a key instead of a click", so it will reach for Esc and kill itself. Stealing a key is also the opposite of "invisible".

**Fix (small).** Hold Escape only while Tessaya is actually injecting input, or only during a drive. While a key that Tessaya itself sends is going out, set a flag in `inputDriver` that the holder ignores. Both are a few lines. Better still: stop is already reachable by voice ("stop"), the pill and the tray, so hold Esc only during a drive.

**Proof on the device.** Ask the assistant to "open Notepad's File menu, then close it". The turn log shows `press_keys escape`. Today the turn ends with no reply and the menu stays open. After the fix the menu closes and the turn goes on.

**Status.** Fix.

### CU-4: hands input runs through a long-lived PowerShell and the plain clipboard, while the sidecar already does it better. Typed secrets land in Windows clipboard history.

**What is wrong.**

- Every Windows click, key and typed string goes through a hidden `powershell.exe` that compiles C# with `Add-Type` when it starts (`inputDriver.ts:91-134`, `:244-249`). Typing is done by pasting through **Electron's clipboard** (`createPaster`, `:192-233`), with a fixed 150 ms wait and a 400 ms restore.
- The Rust sidecar that is already running has:
  - a hardened paste (`paste_windows.rs`), adapted from Handy, which waits for the target to read the clipboard;
  - the "do not keep" formats `ExcludeClipboardContentFromMonitorProcessing`, `CanIncludeInClipboardHistory=0` and `CanUploadToCloudClipboard=0` (`paste_windows.rs:434-436`);
  - a target-window check (`main.rs:977-987`, `should_paste`);
  - `enigo` linked (`Cargo.toml:17`), with the 100 ms modifier hold that some systems need (`keys.rs:1-2`, `:17`).

  The hands use none of it.

- Consequences:
  1. **Everything Tessaya types, including vault secrets** (`vaultHost.type` → `driverFor().type`, `ScreenCompanion.ts:1866-1868`), is written to the clipboard without the exclusion formats. It therefore appears in Win+V clipboard history, and in cloud clipboard sync if he has it on.
  2. Chords press all keys and release them at once, with no hold (`inputDriver.ts:124-129`). The Ctrl+C no-op in #52 fits this pattern. There is no `KEYEVENTF_EXTENDEDKEY` for the arrow, Home, End or Delete keys.
  3. High DPI: the script calls `SetProcessDpiAwarenessContext(-4)` inside an already-running PowerShell and **swallows any failure** (`:115`). If the call fails, `GetSystemMetrics` virtual-screen values and the physical coordinates disagree on a mixed-DPI desk, and clicks land off target with no error. The SOTA doc admits clicks at high DPI were never measured (`computer-use-sota-2026-11-03.md:138-139`).
  4. The first action of a session waits for PowerShell to start and compile (about 1-3 s).
  5. On Linux, every click or key spawns a new `xdotool` process (`inputDriver.ts:173-178`, `:280-309`).

**Why it matters.** The Director asked that it be built inside Tessaya itself, not as helper scripts. The vault promises "you will not see it" (`vault/vaultHost.ts:127`), yet the secret sits in clipboard history. One input path is easier to prove than two.

**Fix (medium: about 150 lines of Rust and 60 of TS, then delete `WINDOWS_INPUT_SCRIPT`).**

- Add an `input` command to the sidecar: `click {x,y,button,count}`, `move`, `down`/`up`, `wheel`, `keys [..]`. Use `SendInput` with the Handy hold and extended-key flags. Coordinates are physical; the sidecar is already Per-Monitor-V2 aware (`main.rs:1169-1171`).
- Route `type` to the existing sidecar `paste` command with `target` set to the window the gate approved. That gives the exclusion formats and fixes CU-2's "wrong window" for free.
- Keep `createInputDriver`'s interface so `runDrivePlan` does not change.

**Proof on the device.**

- Turn on clipboard history (Win+V). Use `vault_use` with `how: "type"` into Notepad. Today the secret is listed in Win+V. After the fix it is not.
- With a 175 % display beside a 125 % display, run `click_element` on a Notepad menu on each display. Compare the hit with `window_at` in the turn log.
- `process_list`/Task Manager shows no `powershell.exe` child of Tessaya after a drive.

**Status.** Fix.

### CU-5: remote hands type into whatever window he is using, and report "focus restored" when it was not

**What is wrong.**

- Remote `type_text` and `press_keys` run `fg.restoreFocus(() => fg.type(text))` (`remoteHandsTools.ts:125-138`). `restoreFocus` records the current foreground, types, then gives focus back to that same window (`ScreenCompanion.ts:1814-1821`). Nothing ever brings the **named target** forward. Keys therefore go to the window the Director is using, which with "I'm away" off may be his chat or his terminal.
- Remote `click_element` by pointer brings the target forward, then hands focus back to his window, so the next `type_text` misses the target again.
- `focus_window` calls `SetForegroundWindow` from the background sidecar (`capture.rs:73-86`). Windows usually refuses that (foreground lock), and the `{error}` result is dropped (`.catch(() => undefined)`, and `focusWindow` resolves with an error object rather than rejecting). The tool still returns "(pointer, focus restored)" (`remoteHandsTools.ts:103`).
- The gate's shell check reads his foreground window, not the target window (`ScreenCompanion.ts:1776-1781`).
- REMOTE_HANDS.md says "No windows, no focus theft … foreground input only when a control has no pattern". The code does not do that for text.

**Why it matters.** It is a remote session typing into the wrong window of a person who is present, with a success message that is not true.

**Fix (small to medium, about 100 lines).**

- Add `set_value {window, label, text}` to `uia.rs`, using `IUIAutomationValuePattern::SetValue` (UFO's `set_edit_text`). That is no focus change and no clipboard. Remote `type_text` with a `window` uses it.
- When a control has no ValuePattern, refuse unless the named window **is** the foreground. Then type with the sidecar paste and `target` set (CU-4).
- Check the `focusWindow` result and say "focus could not be given back" when it fails.
- The remote gate judges the target window's label, not his foreground.

**Proof on the device.** With remote hands on, Notepad in the background and Tessaya Home focused, run `curl … {"tool":"type_text","args":{"text":"x","window":"Notepad"}}`. Today the text lands in Home or the gate refuses it. After the fix Notepad's document holds "x" (check with `ui_tree`), and Home keeps focus.

**Status.** Fix.

### CU-14: every `click_element`/`wait_for` re-reads the whole window, and a timeout is reported as "not there"

- For `wait_for`, use `AddAutomationEventHandler(Window_WindowOpened)` or `StructureChanged`.

### Findings, most important first

#### MEM-1. Per-turn recall mostly repeats the same standing notes and pushes out the relevant memory

**What is wrong**

- `BatonMemoryService.recall` (`apps/server/src/baton/BatonMemoryService.ts:385-417`) always merges a "standing" set into the per-sentence block. That set is every note, preference, correction and decision with confidence 0.6 or more (`:399-402`). Standing items score `0.3 * effectiveConfidence`, which is 0.3 for anything he said himself.
- A text hit scores `(matched words / query words) * (0.5 + 0.5 * eff)`, plus small bonuses (`:228-235`). A spoken sentence with six content words where a stored fact matches one word scores about 0.17. **Every standing note outranks a partially matching fact, learning or episode.**
- The desktop asks for only 300 tokens per sentence (`apps/desktop/src/baton/memory/memoryClient.ts:58-73`). Those 300 tokens are filled with the same notes that are already in the system prompt (`ScreenCompanion.ts:2195-2198` puts `standing()` there at session start).
- `markUsed` then stamps all of them as "used" every turn (`BatonMemoryService.ts:413-415`). So `memory_used` and the "Memory used" card mostly list his standing notes, whatever the answer drew on.
- The recall call is awaited one step after `presence`, before the model is asked (`agentSession.ts:83-90`). That adds up to 800 ms to every spoken turn when the server is slow (`RECALL_MS`).
- Retrieval is FTS5 OR-of-prefixes plus a Jaccard rescore, with no semantic matching (`:211-217`). The stop list is 14 words (`memory.ts:239-254`), so "what", "my", "do" and "me" become prefix terms that match many items. "Who is my accountant" will not find "Sara does the books".
- `scopeRef` is only a +0.2 bonus and the desktop never passes it. Project memories therefore come back in any project.

**Why it matters**
"It remembers what was said, today and before ... so 'type what you just said' simply works" and "he should not have to repeat himself". The per-turn block is the one channel that brings older memory to the model without the model choosing to search, and today it mostly carries the same notes again. The 800 ms also cuts against "still answers fast".

**Fix** (small, under 100 lines)

- In `recall`, leave out the standing set when `text` is given; it is already in the system prompt. Rank only searched hits.
- Drop hits below a floor (for example 0.25).
- Mark only searched hits as used.
- Pass the project or focused session as `scopeRef`, and filter project-scoped items to that project.
- Run `presence` and `recall` in parallel in `agentSession.say` with `Promise.all`.
- Extend the stop list with the conversation module's list (`conversation.ts:66-70`).
- Embeddings are a separate step (MEM-13).

**Prove on the laptop**

1. Add six preferences in his own words, plus one fact: "The accountant is Sara Khan".
2. Ask "when is my accountant meeting".
3. Check the turn log (`agent_turn`) and `memory_used`. Today it lists the six preferences and not Sara. After the fix it lists Sara only.
4. Compare `firstTokenMs` before and after.

**Status:** fix.

#### MEM-2. "Today and before" is not carried: interrupted turns are lost, older talk is never brought in, and a recycle drops 34 turns without a summary

**What is wrong**

1. **An interrupted or failed turn is never written to the conversation file.** `agentSession.say` writes the turn only after `agent.ask` returns (`apps/desktop/src/baton/agent/agentSession.ts:91-108`). On barge-in or Esc (`SessionClosed`), or a failure after the first token, `agentTurn` returns through `fail(error)` (`ScreenCompanion.ts:~2252-2266`) and the conversation never gets his sentence or the partial reply. Only the diagnostic turn log does. He talks over it, which is a designed feature (full-duplex), then says "type what I just said". The words are not in the file, and after a recycle they are not in the session either.
2. **The session is recycled every 40 turns or 6 hours** (`agentSession.ts:12-19`). The new session is seeded only with `RECENT_TURNS = 6` (`agentSession.ts:72`, `conversation.ts:47`). `agentSystemPrompt` takes `earlier`, but it is never passed. #### MEM-4. A correction he gives in conversation loses to his older note, and the extractor cannot see what it is replacing

**What is wrong**

- The contradiction lookup is a free-text search over every kind and scope with Jaccard at least 0.4 (`BatonMemoryLearning.ts:84-90`). It can supersede an unrelated item that shares words, or miss the real one.

### How this compares with OpenClaw, Hermes and current practice

From my own knowledge of these projects, not re-checked against their first-party docs today.

- **OpenClaw.** Memory is plain markdown in the workspace: a curated `MEMORY.md` plus daily `memory/YYYY-MM-DD.md` logs. Search is hybrid (vector plus BM25). It runs an automatic "memory flush" turn before context compaction, so durable facts are written before the context is dropped. Tessaya has the editable-text part as an export only, and has **no flush on recycle** (MEM-2).
- **Hermes Agent.** Small, bounded `MEMORY.md` and `USER.md` are injected as a snapshot at session start. The agent curates them itself (add, replace, remove under a character cap). `session_search` is FTS5 over every past session, with a model summary of the hits, and it nudges itself to save memory. Tessaya's standing block matches the first idea. Its conversation search is local and keyword-only, with no summary step and no cross-device reach (MEM-2, MEM-13).
- **Mem0 / Zep-style practice.** Extract against the top similar existing memories with ADD/UPDATE/DELETE/NONE decisions, and keep facts with valid-time so "the newer one wins" is a data rule. Tessaya has the right fields (`supersededBy`, provenance, confidence) but asks the extractor blind (MEM-4).
- **Where Tessaya is ahead.** Explicit provenance and a "Why?" on every item, a single refusal door for secrets and banking data, tombstones that keep a forgotten item forgotten through sync, held proposals for untrusted input, and the vault offer. Muse's "memory as editable files" lesson is only half met: the tab is editable, but the store is SQLite, and the markdown export is lossy (MEM-8).

### Verdict in one paragraph

The assistant really is one loop: one warm `claude -p` process with 72 Tessaya MCP tools, the built-in file, shell and web tools, and Chrome, all behind one gate (`agentGate`, shared by MCP and harness calls). That part matches the vision. Three things around it do not. First, sentences handled outside the loop are invisible to it. Second, several "tools" are English sentences pushed back through the old router and intent grammar. Third, the stop-gap router is still the fallback. Monitoring is the weakest layer: "watch" only sees work sessions, never his real terminal sessions; crash and resume outcomes are thrown away; and every notice runs on the desktop, only while T3's window is up. The live-session mirror is careful, but message delivery has five separate paths, each with its own queue and safety rule. Four concrete message-loss bugs are among them (ORC-4, ORC-5).

### Findings, most important first

#### ORC-1. The warm assistant never sees turns it did not answer, so "type what you just said" can fail

**What.** The conversation file goes to the model only when a session starts (`agentSession.ts:70-73`, `agentSystemPrompt({ recent })`). Each later turn sends only the context line, the recall block and his sentence (`agentSession.ts:91-99`). Everything other code writes to the conversation log meanwhile stays out of the warm session's context until the next recycle (40 turns or 6 h, `agentSession.ts:12-13`). That includes:

- the "what needs me" fast path. It is a regex (`needsMe.ts:232-247`), checked before the assistant in `ScreenCompanion.ts:2323`, and its reply is written to the log at `:2301`.
- the older router when the assistant fails (`ScreenCompanion.ts:2266-2287`), and refusals (`:629`, `:2365`).
- teach and drive turns, and `remember_target` notes (`:610`, `:2157`).

The prompt nevertheless tells the model "the words are in the conversation below, in full" (`agentPrompt.ts:28`).

**Why it matters.** The vision says "one continuous agent that holds the whole conversation", and his 11-01 bar is "so 'type what you just said' simply works". Today: ask "what needs me?" (regex path), then "type that into the chat". The agent has never seen the list. The regex is also exactly what "Intent over keywords" rules out.

**Fix (small, ~40 lines).** In `createAssistantAgent.say`, remember the id of the last conversation turn the session has seen. Before each ask, add every newer turn that is not its own to the message as an "(also said meanwhile, data)" block. Then either drop `isNeedsMeAsk` and let the agent call `needs_me` (it is already a tool), or keep the fast path, since the next agent turn will now carry its result.

**Prove it.** On the laptop, say "what needs me", then "type what you just told me into Notepad". The turn log's `agent_turn` should show `type_text` with the needs-me words.

**Status.** Fix.

#### ORC-2. The session tools are English sentences sent back through the old router and intent grammar

**What.** In the one assistant's tool host:

- `session_send(id, text)` becomes `actions.act(\`Tell ${name}: ${text}\`)`.
- `session_show` becomes `act("What's X doing?")`.
- `fleet_status` becomes `act("What needs me?")`.

All three are in `ScreenCompanion.ts:2105-2120`. `act` runs `typedRouter.route({kind:"command", text})` (`DesktopBatonVoice.ts:2050-2074`). That is the voice router, which resolves the text through the renderer (`kind:"resolve"/"run"`) into the server's IntentService grammar and model interpreter. When the router asks for confirmation, a second "Go ahead / Not now" box opens after the gate has already judged the call (`DesktopBatonVoice.ts:2061-2068`).

**Why it matters.** "Router routes ... are the design being replaced." Here the router is hidden one level down. The agent passes structured arguments (id, text). They are flattened to prose and re-parsed by a grammar, so a message containing "tell", a colon, or a session name with spaces can route wrongly, or not at all. A send can also be confirmed twice.

**Fix (small to medium, ~120 lines).** Point these three host methods at the structured paths that already exist. For send, use `baton.sessions.send` (SessionCatalog `send` by session id) or the herdr send RPC the Sessions row already uses. For show and status, read the fleet RPC (`baton fleet get`) and use `describeWatch`/`answerNeeds`, as `needs_me` already does. Delete the `act` wrappers.

**Prove it.** Ask "tell the build session: rerun tests: all of them". The turn log should show one gate decision and the exact text arriving in the pane, with no `typedRouter` trace.

**Status.** Fix.

#### ORC-3. Five ways to type into a session, each with different safety rules, and one retries a non-idempotent send three times

**What.**

1. Sessions row and assistant send go through `herdrSend` and `HerdrAdapterLive.sendInput`: blind `pane send-text` and then `send-keys enter` (`HerdrAdapterLive.ts:524-551`). There is no check that the pane is waiting on a permission question or holds a draft.
2. The live-thread composer goes through `baton-live-acp.mjs`, `typeInto`, `herdr agent prompt`. Herdr refuses that with `agent_blocked` while Claude Code asks something, and the script has its own file queue (`baton-live-acp.mjs:722-737`, `503-632`).
3. Weave reads the pane, types only into an empty input, and keeps an SQL queue (`BatonWeaveService.ts`).
4. SessionCatalog `send` keeps an in-memory `waiting` map (`SessionCatalog.ts:102-104, 349-387`).
5. The server's `appendLiveQueue` writes into the ACP script's file queue (`BatonLiveQueue.ts`), with no lock, as the file itself admits.

On top of path 1, `sessionsBridge.act` resends the same "send" up to 3 times, each after a 4 s timeout (`sessionsBridge.ts:23-25, 113-116`). A slow herdr discovery (several CLI calls) can therefore type the message twice.

**Why it matters.** Path 1 is how the assistant and the Sessions row reach a pane. A message whose first character is a digit, or the plain Enter after it, can answer a Claude Code permission prompt that happens to be on screen. That is the form-question class of incident from this week, reached from another door. It is also the "fixes layered on fixes" pattern: each path got its own guard when it broke.

**Fix (medium; mostly deletion, ~250 lines touched).** Use one server service, `LiveSend.deliver(sessionId | pane, text)`, built on the ACP script's rules:

- `herdr agent prompt`, which is refused while a question is up;
- a per-session durable queue;
- the drain rules.

Point the SessionCatalog send, `herdrSend` callers, weave's local box and the Sessions row at it. In `sessionsBridge.act`, retry only `open`, never `send`.

**Prove it.** Leave a Herdr Claude session sitting on a "Do you want to proceed? 1. Yes" prompt. Send "1 more thing" from the Sessions row, and then via the assistant. Today, path 1 types it into the prompt. After the fix, the message is queued with the "a question is waiting" note.

**Status.** Fix.

#### ORC-4. Four ways the live-message queue loses or doubles messages

**What.**

- **(a) Drain overwrites new messages.** `drainSession` reads `[head, ...rest]`, awaits `typeInto` (seconds), then writes back `rest` from before the wait (`baton-live-acp.mjs:614-618, 625`). Anything `prompt()` enqueued in the same process during that wait (`:1030, :1049`), or the server's `appendLiveQueue` wrote, is overwritten and lost silently. Two quick sends to a busy session are enough.
- **(b) Several drainers.** Every ACP process calls `startDrainer()` at start (`:1151`), and each drainer walks every session's file in the shared dir (`:1095-1111`). T3's ACP runtime spawns a process per provider session (`packages/provider-acp/src/server/AcpSessionRuntime.ts`). With two live threads open, two drainers can both read the same head and type it twice.
- **(c) Image-only messages vanish.** An unbound image-only message is kept with `text: ""` (`keptEntry`, `:906-913`; only the words are stored, no attachments). The server's `readKept` drops empty text (`UnboundMessages.ts:58`), so the thread says "Your message was kept" and it is gone. Evidence on this box: all 6 lines of `~/.t3/baton/live-queue/unbound-messages.ndjson` have `"text":""`, and there is no ledger file.
- **(d) Two different queue folders.** The script hard-codes `~/.t3/baton/live-queue` (`:507-508`). The server uses `stateSubdir()`, which picks `~/.t3/tessaya/live-queue` when neither folder exists (`stateDir.ts:27-31`, `BatonLiveQueue.ts:16-18`), and `keptDir` is fixed once at mirror start (`LiveSessionMirror.ts:1790`). On any fresh install (every public user) or after `state-migrate.sh --queue`, the server writes and reads one folder and the script another. Unbound Retry, weaves to live threads and server notes never meet. This box works today only because `~/.t3/tessaya` does not exist yet.
- **(e) Weave reports "delivered" for a message it drops.** A weave to a plain-terminal session returns `delivered: true, "queued ... typed when the session is in a Herdr pane"` (`BatonWeaveBoxes.ts:93-101`). The drainer treats `pane === null` as gone and hands the message back as lost after 10 passes, about 30 s (`baton-live-acp.mjs:600-608`). It is only drained at all if some ACP process happens to be alive.

**Why it matters.** "Nothing he said is ever lost" (11-01 bar). The docs claim these paths are durable.

**Fix (small, each under 40 lines).**

- (a): re-read the queue after the await and drop only the head by its id or timestamp.
- (b): take one lock file (`O_EXCL` with a pid, reclaimed when stale) around a drain pass.
- (c): keep the composed body with `@inbox` refs, and stop dropping empty-text entries that carry refs.
- (d): have the server pass `BATON_LIVE_QUEUE_DIR` in the provider instance env (`ensureProviderInstance`, `LiveSessionMirror.ts:821-826`), or make the script use the same `stateSubdir` rule.
- (e): live box returns `delivered:false, queued` and the drainer keeps (never drops) items whose session is alive without a pane.

**Prove it.**

- (a): unit test with a fake `typeInto` that enqueues during the await.
- (d): on a clean Windows or Linux profile, send in an unbound live thread, then check that Retry appears and works.
- On this box: send an image-only message in an unbound thread and look at the kept file.

**Status.** Fix.

#### ORC-5. On machines without Herdr (his Windows laptop), sending to a stopped session drops the message after telling him it is kept

**What.** `SessionCatalog.send` puts the text in `waiting` and calls `resume`. With a thread port (no Herdr), `resume` gives up waiting after 8 s and answers "resuming". The caller is told "your message is kept and goes when it is ready" (`SessionCatalog.ts:337-347, 378-383`). When the import finishes with `pane === null`, `waiting.delete(sessionId)` throws the message away (`:331`), and nothing sends it to the new thread. The "failed ... Your message is kept" branch keeps it only in memory, with no retry and nothing that survives a restart (`:384-387`).

**Why it matters.** Windows is the Director's main device, and this is the "send to any session from anywhere" priority (P1).

**Fix (small, ~30 lines).** When the resume yields a `threadId`, send the waiting texts with `engine.sendMessage` to that thread (the watchdog already does this for its restart notice, `BatonSessionCatalogService.ts:452-459`). Persist `waiting` in the same file folder as the queue.

**Prove it.** On the laptop, stop a session, send "hello" from Sessions, wait for the import, and check the thread has "hello".

**Status.** Fix.

#### ORC-6. Monitoring cannot see his real sessions, throws away crash outcomes, and only runs while the desktop window is up

**What.**

- **Watch covers work sessions only.** `watchFleet` reads only `entries`, and `buildBatonFleet` builds those from work sessions only (`fleet.ts:76`). Live terminal sessions (every mirrored `baton-live4:` thread) and plain T3 threads therefore never appear as failed, stalled or unanswered (`watch.ts:35-79`). The same goes for `watch_report`, notices, the morning brief and initiative triggers.
- **Watchdog results are discarded.** The auto-resume watchdog computes `resumed` and `skipped` (with reasons like "already resumed three times this hour"), and `SessionWatchdog.ts:13` throws the result away. No log, no finding, no notice. A crash-looping session is silently capped.
- **Row states miss crashes.** Desktop session rows have only `working | waiting | idle` (`sessionRows.ts:31`). A crashed session just disappears.
- **All noticing is on the desktop.** `checkAttention` (5 min), initiative (2 min) and playbook (2 min) run in the desktop app and return early unless T3's main window exists (`DesktopBatonVoice.ts:2988-2990`). The server boxes where sessions "run for days" never tell anyone.
- **No plan-ready trigger.** "Job plan ready" has no trigger at all (`initiative.ts` trigger kinds), although the vision says Tessaya "says briefly over voice that it is ready, pointing him to that thread".

**Why it matters.** This is the vision's monitoring line verbatim: "keeps track of sessions ... so they're not left unattended forever. It knows if they crashed, failed, or what they did ... through proper monitoring", plus Stage 5's "what needs me?" across every project.

**Fix (medium, ~200 lines).**

1. Write each watchdog outcome to a small server ring buffer (and to `baton-mirror.ndjson`) as `crashed`, `resumed` or `gave_up` findings.
2. Add live-session findings to the `watch.get` answer: waiting for more than N minutes (the mirror already knows `status === "waiting"` and the pane question), died mid-turn, auto-resumed, resume capped.
3. Add a `job_plan_ready` initiative trigger off `awaiting_agreement`.
4. Later: let the server push findings over the existing relay alert path, so a closed laptop does not mean silence.

**Prove it.** Kill (by its own pid) a Herdr Claude session mid-turn on the second server. Within about 2 minutes, "is anything stuck?" should name it as crashed and resumed (or why not).

**Status.** Fix. Server-push is blocked on choosing the alert channel.

#### ORC-7. One bad registry read archives idle live threads, and they are never unarchived

**What.** `endedMirrorThreads` archives a mirror thread when its session is missing from this tick's read and the thread was last updated more than 5 minutes ago (`LiveSessionMirror.ts:520-535, 1858-1865`). The grace therefore measures how long the thread has been idle, not how long the session has been missing. One read that misses a session archives at once every live thread idle for more than 5 minutes:

- `readClaudeLiveSessions` returns `[]` on a readdir error (`ClaudeLiveSessions.ts:176-180`) and silently skips a descriptor that is mid-rewrite (JSON parse fails, `:31-34`).
- An account rotation or Herdr adoption restarts the process under the same session id (D69, D74), which leaves a gap between ticks.

Nothing in `apps/server/src/baton` ever unarchives a thread (grep finds only the WorkSession `unarchive`). When the session reappears, `startFollowing` mirrors into the hidden archived thread.

**Why it matters.** It is the thread-list version of "nothing lost". The thread he is talking to disappears from the sidebar after a rotation.

**Fix (small, ~30 lines).** Keep `missingSince` per session id in the mirror, and archive only after it has been missing for 3 or more minutes of consecutive successful reads. In `startFollowing`, if the shell is archived and the session is live, dispatch `thread.unarchive`.

**Prove it.** Rotate the account of a live session idle for more than 5 minutes (`cswap`). The thread must stay in the sidebar, and the mirror log must have no archive line.

**Status.** Fix.

#### ORC-8. Turn state leaks between sentences in the one loop: taint reset mid-turn, sticky tool bans, double execution on fallback

**What.**

- **(a) A second sentence resets the running turn's state.** `say()` calls `beginTurn()` before awaiting the session (`agentSession.ts:80`), while `ask` is queued behind the running turn (`claudeVision.ts:369-389`). A second sentence spoken during a turn therefore resets the running turn's taint, typing scope and tool logs (`ScreenCompanion.ts:2201-2209`). After that reset, a `type_text` of text the running turn read from a page or file is judged untainted and is not asked. The gate rule "typing text you got from a screen, a file or the web ... not yours without his yes" (`agentPrompt.ts:36`) is bypassed by timing alone.
- **(b) Failed tools stay banned for hours.** `withFailureGuard`'s map lives for the whole session, up to 40 turns or 6 h (`failureGuard.ts:11`), keyed by tool and arguments. After two failures of `screen_capture({})` or `ui_tree({})`, those tools are refused for hours, while the prompt says "a tool that fails is not a tool that is missing".
- **(c) Fallback re-runs actions.** The router fallback re-runs the sentence whenever no text token arrived (`ScreenCompanion.ts:2266`). A turn that already clicked, typed or sent and then timed out or crashed is executed a second time by the old router.

**Why it matters.** It is the one loop's safety and reliability. A "capable person in the room" does not repeat an action, or give up on a tool for six hours.

**Fix (small, ~25 lines).**

- (a): run `beginTurn()` inside the serialized chain, just before the message is written to stdin. For example, pass it as a callback to `ask`, or queue `say` calls.
- (b): clear `failures` at `beginTurn`.
- (c): fall back only if `agentTools.length === 0`.

**Prove it.** Unit test (a) with a fake session that resolves the first ask late. For (b): on the laptop, unplug the second monitor, ask twice about it, plug it back in, and ask again; `screen_capture` must run.

**Status.** Fix.

#### ORC-10. The always-on assistant's server tools depend on T3's React sidebar being mounted

**What.** Jobs, memory, commitments, weave, cloud, phone and session catalog calls go from Electron main to `webContents.send` and are answered by `useEffect` subscribers in `BatonIntentBar.tsx:149-197` and `BatonProjectsBlock.tsx:159-188`. **Fix (medium to large).** The desktop bundles and starts the server, so it knows the local origin and can mint a token. Give the main process a small RPC client for the `baton.*` methods. Keep the renderer bridge only for clicks that must navigate. Do this after ORC-1 to ORC-8.

#### ORC-11. Polling cost, and one slow pane stalling every mirror

**What.**

- **The 2 s tick does a lot.** It reads every config dir's registry plus `/proc/<pid>/environ` per session. It loads the full thread-shell snapshot for `endedMirrorThreads`. It runs `stampKept` twice (`:1821` and `:1793`), each reading two ever-growing NDJSON files; while any orphan entry exists, that also calls `activeProviderThread` for every live thread. Per session it runs `threadShell` (retitle) and up to two node+herdr spawns while waiting.
- **The tick is sequential.** `Effect.forEach` runs without concurrency (`:1869-1904`). A pane read can take 10 s plus 10 s on timeout, so one hung pane delays mirroring of every other session.
- **The watchdog stats every transcript.** It scans every transcript each minute: 29,403 `.jsonl` on this box (`SessionCatalogLive.ts:22-93`, synchronous fs on the server's event loop, 15 s cache). The desktop catalog refresh adds another list every 45 s per environment.
- **The desktop job poll never stops.** Its job refresh runs every 15 s across all environments forever, once the Jobs tab has been opened once (`DesktopBatonVoice.ts:2951-2977`).
- **The `mirrorLog` dedupe map grows forever.** Its keys contain timestamps (`rebound:...:${nowMs}`, `kept-resent:...:${Date.now()}`).

**Why it matters.** "Performance without compromise" (AGENTS.md), and fewer false alarms when ticks lag.

**Fix (small to medium).**

- Run per-session steps with `{ concurrency: 4 }`, with a per-session timeout.
- Fetch the shell snapshot once per tick, or every 30 s for the ended-thread check.
- Call `stampKept` once, and only when the kept file's mtime changed.
- Read the pane only when the descriptor's `updatedAt` changed.
- Run the transcript scan incrementally, by directory mtime.
- Poll jobs only while the Jobs or Approvals tab is visible.
- Key `mirrorLog` dedupe only for the repeating records.

**Prove it.** Add a `tick-ms` line to `baton-mirror.ndjson` (or measure it). With 3 live sessions and one sitting on a question, tick duration and `pidstat` CPU should drop.

**Status.** Fix.

### Jobs end to end (asked explicitly)

The jobs pipeline exists and is real on the server:

1. `job_start` goes through the renderer to `BatonJobFlow.startJob`. It is idempotent: a retried start finds its thread. The thread opens in plan mode with his words verbatim and the operating-system pack's planning frame.
2. `BatonJobReactor` notices the finished plan from thread events, then enforces time and turn caps, auto-retries and posts reports every 45 s.
3. `job_agree` leaves plan mode and sends "go ahead". Refine, schedule, split (coordinator), handoff and skill draft are wired too.

Missing against the vision:

- the spoken "it's ready, see that thread" (ORC-6);
- any notice when the desktop is closed (ORC-6);
- the routing of every job call through the renderer (ORC-10).

`job_start` needs the exact project label; the error lists the projects, so the agent can recover.

### Already fine; leave alone

- **One gate.** `harnessGate` delegates to `agentGate` for built-in tools and lets Tessaya MCP calls through to the same gate inside `batonMcp`, so file, shell, web, Chrome and Tessaya tools share one taint and one judge. Refusals are final and logged.
- **The MCP server.** It is bound to 127.0.0.1 on a random port, with a per-session bearer token, Host check, no Origin, 1 MB body cap, vault scrub on output, and the token file mode 0600 (`batonMcp.ts`, `claudeVision.ts:254-276`).
- **One question at a time per session** (`claudeVision.ts:367-389`). A timeout kills the session rather than misattributing a late answer. Esc disposes the agent cleanly (`dropOperator`).
- **The conversation log**: rotated at 20 MB with both files read, and the session re-seeded on recycle (`conversationLog.ts`).
- **Binding heal.** `decideBinding` is pure and tested, the 30 s heal works, and the decisions are written to `baton-mirror.ndjson`. Evidence: on this box one `rebind-native` on `cc828d1b` at 01:08:57, and stale asks expired at 01:36 and 04:51. Keep the mirror log; it is the best debugging aid in this area.
- **The question card path.** A plain message is never taken as a form answer (`isCardAnswer`). Cards are tied to a run (`askRunId`), and stale cards are expired. `herdr agent prompt` refusing while blocked is the right primitive (see ORC-3).
- **Auto-resume rules** (`AutoResume.ts`): tail classification, a 2-minute grace for deliberate stops, a 3-per-hour cap, at most 2 per pass, "seen live" memory, and a stop marked on purpose is respected. Only the reporting is missing (ORC-6).
- **Job flow semantics** (above), and `RetireHandoff`'s step-by-step idempotent retire with an undo file.
- **Desktop lifecycle**: the main-thread stall worker and the heartbeat. `remoteHandsLoop` long-polls (25 s server wait), so it does not spin.

## Tessaya review, lane 4: INTELLIGENCE (prefix INT)

### Findings, most important first

#### INT-1. A natural spoken "yes" is not a yes: confirmations use a strict regex, and anything else cancels the question and becomes a new command

- **What is wrong.** Risky actions are confirmed out loud through `askLocal`, then `actions.confirm`, then the voice core's pending confirmation (apps/desktop/src/baton/screen/ScreenCompanion.ts:846-869). The answer is judged by `AFFIRM` and `DECLINE` (packages/baton-voice/src/modeMachine.ts:127-130). `AFFIRM` accepts only `confirm(ed)`, `yes`, `yes do it/confirm/go ahead`, `go ahead`, `do it` and `approve(d)`. "Yeah", "yep", "yes please", "sure", "go on then", "go for it", "please do" and "yeah, send it" all fail it. Those fall through to line 362 ("Anything else is a new instruction; the old question lapses"). The pending ask then resolves to `expired` (core.ts:299-300), `spokenOutcome` returns null (operator.ts:494-498), the card stays up, and his "yeah go on then" goes to the assistant as a brand-new command. `DECLINE` has the opposite fault: it matches on the first word, so "no, send it to Sam instead" or "don't forget to cc me, yes" are taken as a plain no.
- **Why it matters.** "It acts on simple work and confirms risky work in conversation, out loud." "Must be smart": the 09-18 ruling was that he should never have to learn the machine's shapes. He speaks British-leaning English (memory/director-voice-accent.md), and "yeah, go on" is the most likely way he will say yes.
- **Fix (small, under ~80 lines).** Keep the deterministic default of no. Widen the clear-yes list to cover yeah, yep, yup, sure, yes please, go on (then), go for it, please do, ok do it, and send it/do it with "please". Anchor `DECLINE` to the whole utterance, as `isDismissPhrase` already does. For anything else while a confirmation is pending, ask once more ("Was that a yes?") instead of superseding it. If a model is wanted, use the cheap model as a three-way classifier (yes, no or other) given the question, and treat only "yes" from both the model and a whole-utterance check as yes. Add rows to modeMachine.test.
- **Prove on device.** Turn on spoken output and leave "act without asking" off. Ask Tessaya to type a line into Notepad. When it asks, say "yeah go on then". Expect the card to close as yes and the text to be typed. In the turn log, the second sentence should not appear as a new `agent_turn`.
- **Status.** Fix.

#### INT-2. In the follow-up window, replies are dropped by a first-word keyword list, including answers to Tessaya's own clarifying questions

- **What is wrong.** After an answer, the window stays open. A sentence said there without the wake word is kept only if `isAddressedFollowUp` passes (packages/baton-voice/src/core.ts:447-454, packages/baton-shared/src/followUp.ts:8-31). It passes when the sentence ends in "?", contains "tessaya/baton/assistant", starts "I want/let's", or its first word is in `OPENERS`. Everything else is dropped silently with reason "not addressed". Words like "the", "it", "that", a project name, "Snowdon", "Wales" and "Notepad" are not openers. So when the assistant asks "Which one do you mean?" (the router's clarify route, or the one assistant's "ask one short question"), the natural reply "the scheduler one" or "The Margin" is thrown away. The file's own header promises "a continuation of the topic", which is not implemented. Parakeet only adds "?" to a real question, so "and in Wales" as a statement is dropped too.
- **Why it matters.** "Intent over keywords: nothing fires on a word alone." The same applies to dropping on a word alone. "He should not have to repeat himself."
- **Fix (small).** When the last reply ended in a question, or the last turn was a clarify, accept the next utterance in the window unconditionally. Otherwise keep the TV guard. Better: let the cheap model judge "addressed or not" from the last exchange, with the current list as the fast yes-path only. Add cases to the follow-up tests.
- **Prove on device.** Say "Freya, start a session" with two projects open. When it asks which project, answer "The Margin" with no wake word. Expect it to proceed. Today the turn log shows `dropped … not addressed`.
- **Status.** Fix.

Narrow `isNeedsMeAsk` to needs-me wording (drop "my approval"), or route approval asks to `approvals_list` too. #### INT-7. The intent layer's learning loop is one-way, binds to stale ids, and is off the main voice path

- **What is wrong.**
  - `learnFromReading` (IntentService.ts:520-566) stores every model reading that ran and did not fail, as a full command JSON with concrete `workSessionId`, `firingId` and `providerInstanceId`. Replay (lines 366-384) returns that command verbatim when the grammar refuses the same normalised words. It is never re-checked against the current vocabulary and never re-resolved for "it" or "that one". So "tell it to stop" learned once is bound to whatever session was focused that day, for ever. The prompt's own rule ("'it' means the work the user is looking at", intentModel.ts:218) is bypassed.
  - The repository has `find`, `list`, `learn` and `markUsed` only (IntentVocabularyRepository.ts:58-70). There is no forget or correct, and no UI, so a wrong reading cannot be unlearned and outranks the model for ever.
  - With `oneAssistant` on, the desktop assistant has no tool that reaches `IntentService.run`, so learned phrasings and the grammar serve only the web intent bar, mobile and the router fallback.
  - `INTENT_MODEL_OPTIONS` (thinking off, measured 10.0 s against 6.0 s) is declared and never passed (IntentInterpreter.ts:82). `BatonOneShot` runs bare `claude` with the ambient config (BatonOneShot.ts:56-74), so the signed-in instance that `chooseInterpreterInstance` carefully picks is used only as a yes/no gate. The expired-token lesson in its comment is not actually applied.
- **Why it matters.** "Confirmed sentence→command pairs are learned into the fast path" (09-18 ruling). The vision calls learnings "a constant feedback loop". A loop that cannot be corrected, and that replays stale targets, makes it confidently wrong.
- **Fix (small to medium).**
  1. Store the learned pair as words to kind plus a description, not ids. On replay, re-resolve ids against the current vocabulary (or hand the learned pair to the model as a few-shot example, which it already does). Drop the pair when an id no longer exists.
  2. Add `forget(normalisedText)` and list learned phrasings in the Memory tab.
  3. Pass the thinking option, or `--settings {"alwaysThinkingEnabled":false}`, and the chosen instance's config dir to `BatonOneShot`.
- **Prove on device.** From the web intent bar, say a phrase the grammar refuses that targets session A. Focus session B and say it again. Today it goes to A. After the fix it goes to B, or asks.
- **Status.** Fix.
